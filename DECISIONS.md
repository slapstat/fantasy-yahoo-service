# Decision log

Non-obvious choices in this service, one line each. Format and rules: the monorepo root `DECISIONS.md`.

[2026-09-11] fantasy-yahoo-service: an unknown path answers 404 through its own `NoResourceFoundException` handler, copied from bff and espn-service (fantasy-workspace#33) — a shared advice library was rejected because the services deploy separately and it would couple their releases for about ten lines, and a catch-all that passes every Spring `ErrorResponse` 4xx through quietly was left for a separate decision across all four services rather than widening this fix.
[2026-09-11] fantasy-yahoo-service: the four OAuth secrets are checked by Bean Validation on `YahooOAuthProperties` at binding (#45), including the 32-byte key length — a `@PostConstruct` check like `InternalApiKeyFilter`'s was rejected because it would sit in whichever bean happens to read the value, and a check in the record's constructor because unit tests build the record by hand with blanks; both staging and prod containers were confirmed to carry all four, non-blank, before merging.
[2026-09-11] fantasy-yahoo-service: the sync flag is claimed in `SyncService.startAsync()` before the thread starts, and a busy `sync()` returns empty instead of throwing (#44), ported from espn-service#16 — keeping the controller's `isRunning()` pre-check plus a quieter log was rejected because the check-then-act gap stays open, and the scheduler overlap is a skip at INFO, not a failed run, because the run under way does the same work.
[2026-09-11] fantasy-yahoo-service: only a dedicated `YahooUpstreamException`, thrown by `YahooFantasyClient` and `YahooTokenClient`, maps to 502 (#47) — rewording the config and crypto paths was rejected because it fixes those instances and leaves any future `IllegalStateException` blamed on Yahoo, and `YahooGrantRejectedException` stays separate rather than a subtype because its remedy is re-consent, not retry.
[2026-09-11] fantasy-yahoo-service: local `docker-compose.yml` moves from `postgres:17-alpine` down to `16-alpine` to match what Coolify runs in staging and prod, checked on both servers (#46) — upgrading the servers to 17 was rejected as a data migration on two live databases for no feature this service uses, while a local mismatch can hide a version-specific difference until deploy.
[2026-09-15] fantasy-yahoo-service: a 403 from the Fantasy API becomes `YahooAccessDeniedException` and is answered as 403 with Yahoo's `error.description`, logged at WARN — from 2026-08-26 to 2026-09-15 Yahoo's app-level refusal went out as a 502 "upstream failure" and read as an outage; making it a `YahooUpstreamException` subtype was rejected because the advice would still have to tell the two apart and a refusal's remedy is Yahoo's grant, not a retry, and ERROR was rejected because a user whose own account is refused is not our fault while a lost app permission still reaches ERROR through the sync's failed run. The token endpoint's failures are unchanged.
[2026-09-16] fantasy-yahoo-service: the OAuth callback parks tokens under a one-time link code that the signed-in web claims through the BFF, and only the user who started the flow may claim it (a different user's claim discards them) — a cookie set on yahoo.slapstat.com by a start redirect was rejected because it needs a second public route on that host, and binding the state to a browser the web holds cannot work since the callback runs on another host; the code rides in the URL fragment so no server log or Referer sees it.
[2026-09-16] fantasy-yahoo-service: the container runs as `app` with a fixed UID/GID of 10001, given numerically to `USER`, instead of root — the base image's existing `ubuntu` user (1000) was rejected as an account the image's maintainers own and may change, and handing the user a writable `/app` was rejected because the service writes only to `java.io.tmpdir` (/tmp), so the unpacked jars stay root-owned and read-only to it.
[2026-09-17] fantasy-yahoo-service: the connection status reports not connected when the stored refresh token cannot be decrypted, logged at WARN, and still keeps the row — after the 2026-09-16 key rotation staging showed Yahoo as connected while every league call failed; deleting the unreadable row was rejected because a key that is only wrong for a while would cost every user their connection, and ERROR on the status check was rejected because it runs on every page view while the ERROR a wrong key needs is already raised where the token is used.
[2026-09-17] fantasy-yahoo-service: `GET /api/v1/yahoo/leagues/{key}/free-agents` reads Yahoo's `status=A` (free agents and waivers together) sorted by actual rank, capped at a `limit` the service enforces on the response as well as in the request, and reports `availability` per player (fantasy-web#751) — `status=FA` alone was rejected because it hides the player a rival dropped an hour ago, which is the one a streamer most often wants; the cap rides on the rank sort so a trimmed list loses the tail nobody streams, and it is re-checked while parsing because Yahoo has served fuller pages than `count` asked for.
[2026-09-22] fantasy-yahoo-service: `GET /leagues/{key}/teams` returns the teams in draft order, read from the draft results (the one `out=settings,draftresults,teams` call the draft endpoint makes), because the draft setup imports teams from it and Yahoo's `/teams` lists them by team id — rejected: having the web's setup read `/draft` instead, which is behind DRAFT_LEAGUE_SYNC_ENABLED and would leave every consumer of `/teams` with the wrong order.
[2026-09-22] fantasy-yahoo-service: team draft order falls back to each team's `draft_position` when Yahoo lists no draft-result slots — a league with teams finalized and the draft not yet started answered `predraft` with zero slots, so the earlier fix (#73) left it in team-id order; the slots still win where present, since they carry a traded first-round pick.
[2026-09-22] fantasy-yahoo-service: before Yahoo lists a draft's slots, only the manager's own seat is placed (league metadata `draft_position`) and the other teams keep Yahoo's order; read raw through the probe, a test league with teams finalized carried no slots and no per-team `draft_position` (#74's fallback read a field Yahoo does not send, so it is removed), and the other seats are not in the API at all, so guessing them was rejected.
[2026-09-23] fantasy-yahoo-service: `GET /leagues/{key}/teams` reads the draft's slots again (`out=draftresults,teams`) and answers the manager's seat as its own `draftPosition`, null when Yahoo names it nowhere — a real league with its order set carried the slots while the metadata's `draft_position` disagreed with them, and #77 had just dropped that read on the assumption the metadata sufficed, so the setup silently showed the seat the team happened to sit at in Yahoo's team order (10 where Yahoo's own draft results said 12); rejected: keeping the seat implicit in the list order, because a consumer cannot tell a seat Yahoo named from an index it inferred, which is the whole defect.
[2026-09-23] fantasy-yahoo-service: `/api/v1/sync/probe/league` takes an optional `appUserId` and then reads with that user's token instead of the service account's — the account is in no real league, so every question about what Yahoo sends for a league whose commissioner has set something (a draft order, in the case that prompted this) was being answered from a test league where nobody had set it, and #74's removed per-team `draft_position` was concluded from exactly that; rejected: adding the service account to a member's league (it would read their data for reasons unrelated to the pool, and cannot be done for a league we do not run).
[2026-09-23] fantasy-yahoo-service: the manager's seat comes only from the first round of `draft_results`, and is null before Yahoo lists those slots — the league metadata's `draft_position` is not the draft order and must not be read as it. Probed raw (#80) against a real 14-team league two weeks before a live draft: `draft_status` predraft, `draft_results` empty, exactly one `draft_position` in the whole payload (10) while the league's own draft-results page and its published order both had that manager twelfth, and no per-team position anywhere (`has_draft_grade` appears once per team, `draft_position` once in total). Rejected: keeping it as a best guess behind a "may be wrong" label, since nothing in the payload distinguishes a stale value from a right one, and a wrong seat reorders every round of the draft built on it; rejected too: reading Yahoo's web draft-results page, which is cookie-authenticated and not ours to scrape.
[2026-09-24] fantasy-yahoo-service: `GET /leagues/{key}/draft` says whether its team order is the draft's (`orderKnown`, true only when every team holds a first-round slot of its own), because Draft Mode read a seat off the list and told the manager of a live-draft league "your first pick is #6" two weeks before the draft, from Yahoo's team order, where the league's own order had him twelfth — rejected: leaving `teams` empty until the order is known, which takes away the league's size and team names that following before the draft needs; and true as soon as any first-round slot exists, which counts places past a team holding a traded first-round pick twice.
[2026-09-25] fantasy-yahoo-service: `GET /leagues/{key}/rosters` reads Yahoo's `/league/{key}/teams/roster` (today's rosters, one call) and answers every rostered player, bench and IR/IR+/NA included, with the slot Yahoo has him in (fantasy-bff#315) — filtering to active slots here was rejected because what counts toward a power ranking is the consumer's call and a dropped slot cannot be recovered downstream; a per-team `/team/{key}/roster` call was rejected as N requests for what one league call returns; its ids come from the player key like the draft's, so both land in the pool's id space.
[2026-10-01] fantasy-yahoo-service: a player page that fails to reach Yahoo is retried up to three times (linear backoff, `yahoo.players.page-retry-backoff-ms`, 0 in tests) inside `YahooPlayerService.paginate` rather than in `YahooFantasyClient` (#88) — retrying in the client was rejected because every user-facing league, draft and free-agent call would then wait up to three read timeouts for an answer the user is holding the page for, while the pool read is a background job where waiting costs nobody; skipping the failed page and carrying on was rejected outright because `SyncService.runSync` removes the players it does not see, so a gap deletes them; only `YahooUpstreamException` is retried, which leaves `YahooAccessDeniedException` failing on the first attempt as [2026-09-15] requires, since a refusal's remedy is Yahoo's grant and the off-season switch depends on that 403 being fast.
[2026-10-12] fantasy-yahoo-service: Yahoo's percent rostered is read by the daily sync in a walk of its own (`/league/{key}/players;start;count=25/percent_owned`) and stored per player, for the admins' Streamer Planner demo (fantasy-web#1166) — reading it live per request was rejected because Yahoo cannot filter or sort by it, so every request would page the whole pool, and Yahoo itself updates it daily; splicing `percent_owned` into the stats walk was rejected because mixing an `out=` subresource with the season-pinned `/stats;type=season;season=` path is undocumented, and a failed walk keeps the last run's numbers rather than failing the sync, since only the demo reads them.
[2026-10-13] fantasy-yahoo-service: `GET /leagues/{key}/rosters` takes an optional ISO `date` and asks Yahoo for `teams/roster;date=…`, templated like the league key, while no date keeps the undated call — filling in our own "today" was rejected because Yahoo's day turns over on its own clock, so the undated call stays Yahoo's answer; a parameter that fails to convert (that date, a non-numeric `limit`) answers 400 through a `MethodArgumentTypeMismatchException` handler instead of the catch-all's 500, and extending `ResponseEntityExceptionHandler` to map every Spring 4xx was rejected as the wider change already left open in the 2026-09-11 line.
[2026-10-13] fantasy-yahoo-service: the catch-all answers any Spring MVC `ErrorResponse` with a 4xx status with that status and its headers, the reason phrase as the message and no log, ported from fantasy-bff (its 2026-09-19 line) — this closes the cross-service question the 2026-09-11 line left open: a missing required parameter, an oversized one on `SyncController` (no class-level `@Validated`, so `HandlerMethodValidationException`) and a 405 each answered 500 with an ERROR trace in Sentry. Rejected: extending `ResponseEntityExceptionHandler` (a fixed list, writes ProblemDetail instead of `ErrorDto`, and collides with the handlers already here), and one narrow handler per exception, because each new Spring refusal would be another 500 until someone added one.
[2026-10-18] fantasy-yahoo-service: `YahooFantasyClient.get` retries a call once (two attempts, `yahoo.fantasy.connect-retry-backoff-ms`, 0 in tests) when it fails with a `ResourceAccessException` caused by a `ConnectException`, after one failed connect turned a user's league listing into a 502 (Sentry JAVA-SPRING-BOOT-35) — this narrows the 2026-10-01 line rather than reversing it: that line kept retries out of the client because a user-facing call would wait out repeated read timeouts, and a connect failure is fast and certain that nothing was sent, so retrying it cannot do anything twice; read timeouts and every HTTP error status are still not retried, since the request may have reached Yahoo and a 403 must stay fast for the off-season switch; retrying in the BFF was rejected because every BFF caller would need it and the BFF cannot see the cause chain, only a 502; the `attempt(...)` probes are left alone, since their job is to report the failure as it happened.

[2026-10-18] The connect-failure retry's WARN logs only the root cause's type, not the exception, so `YahooFantasyClient` needs no CRLF_INJECTION_LOGS exclusion (the exception's text quotes the request URL, which FindSecBugs reads as tainted); the trace is not lost, since the last attempt's failure still reaches the caller and its ERROR log whole. The pool sync's page retry (#89, 3 attempts) wrapping this one (2 attempts) is kept as it is: a page that cannot connect is tried at most 6 times, each failure fast, a few seconds in all; rejected exempting connect failures from the page retry (two retry policies to keep in step, for a case that costs nothing).
